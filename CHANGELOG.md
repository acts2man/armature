# Changelog

All notable changes to Armature are recorded here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

JOB-C-COMPLETE

### Added

- **In-app Help ("How Armature works").** A new Help item at the bottom of the agency sidebar opens `/agency/help`: an in-app, searchable guide with an eighth-grade reading level. Ten sections — what Armature is, adding a project, installing and updating the kit (with "every visual check uses the production build"), editing and publishing (draft, publish, one GitHub commit, Netlify rebuild, credit note), where each thing lives (GitHub vs Supabase), giving clients access and editing levels + View as client, SEO and Search Console, email sending setup, storage and what counts against Supabase's included amounts, and troubleshooting (can't connect, editor won't load, publish conflict, site not updating, picture not showing, password reset). Clients get a shorter guide at `/help` ("How to edit your site"). Every entry lives as a markdown file in `docs/guide/agency/` and `docs/guide/client/`, so updating a section is a text edit — Vite bundles the files at build time with `import.meta.glob`, no network calls at runtime. A tiny in-house markdown renderer (`src/lib/markdown.ts`, 9 unit tests) handles headings, lists, code fences, bold/italic, and safe links (https and site-relative only; anything else becomes `#`). Search filters entries by title and body with a snippet excerpt around the match.
- **File storage in Supabase, one folder per client.** A new public Storage bucket (`site-files`, migration `20260924000200_site_files_storage.sql`, not applied here) holds a site's uploaded pictures, PDFs and documents at `<agency_id>/<site_id>/<folder>/<file>`. RLS on `storage.objects` gates writes to that site's folder to agency staff and site members; public read lets published sites link straight to the file through Supabase's CDN. A new **Storage files** panel on `/sites/:siteId/media` uploads (up to 20 MB per file), lists, copies the public URL and deletes; video files are refused with advice to use YouTube, Vimeo or Wistia through the Video widget. Uploads set `Cache-Control: public, max-age=31536000, immutable` so the CDN caches aggressively. A new `site_storage_totals` SQL view surfaces the file count and total bytes per site (respecting the same RLS), used to show "N files, N MB used" next to the upload button. Repo-based images in `public/assets/uploads/` keep working exactly as before — the two libraries coexist. Supabase image transformations stay off (they cost extra). New browser helper `src/lib/siteStorage.ts` (with unit tests) does the upload, list, delete and URL-building; the safe-file-name and storage-path pure functions are covered by unit tests.
- **Auth: branded email, forgot password, view-as banner in the editor.** "Forgot your password?" was already on the sign-in form (it renders below the password field); the reset flow's "choose a new password" step now uses the shared password rules (at least 10 characters; not the word "password", the email address, or one character repeated) rather than a bare 6-character minimum, matching the invite and choose-password screens. Agency settings gains a new **Email sending** panel (agency owners only): a from-name, from-address and reply-to for outgoing email through Resend, a "Send test email" button that mails the caller and records the last successful test date on the agency row (`agencies.email_last_test_at` / `email_last_test_error`, added in migration `20260924000100_agency_email.sql`, not applied here), and the exact three-step setup (verify a domain in Resend, add the `RESEND_API_KEY` secret in Supabase, fill in the from-address). The panel names Resend's free tier plainly (3,000 emails a month, 100 a day, one domain) and always says the feature is optional. The full-screen visual editor now shows the same **Viewing as {name}** banner and Exit button as the dashboard when agency staff "view as" a client (`src/components/ViewAsBanner.tsx` mounted above `EditorWorkspace`).
- **Optional Resend delivery for invites and password resets.** A new shared helper `_shared/email.ts` sends through Resend on behalf of an agency: with `RESEND_API_KEY` set as a Supabase Edge Functions secret AND `agencies.email_from_address` filled in, invites and client password-reset emails go out under the agency's name (`emailed: true`); with either missing, the response is `emailed: false` with a plain-English `email_hint` so the dashboard keeps offering the link to copy, exactly as before. No feature depends on Resend; nothing new is required to run Armature. New edge function `email-test` powers the settings screen's test button. 5 Deno tests cover every path (no key, no address, real send, Resend error, bad recipient).
- **SEO that reaches Google (KIT_VERSION 2.6.0).** Every page's Page settings now carries the full SEO tab: search-result title (with a character counter and a Google-style preview built from the site's URL and title pattern), meta description, canonical URL, noindex/nofollow, Open Graph (Facebook, LinkedIn, iMessage) share title/description/picture, X (Twitter) share title/description/picture, and structured data presets — LocalBusiness / Organization (drawing from the site business details, with per-page overrides), Article (headline, author, dates), FAQ built from an accordion on the page (identified by its element id), and BreadcrumbList. Site settings › SEO adds the site-wide defaults: site name, site URL, default share picture, title pattern (with `%page%` and `%site%`), Google Search Console verification code, default description, robots.txt extras and the LocalBusiness business details (name, address, telephone, opening hours, price range, sameAs). Every field is validated by `kit/validate.ts` (extended for the new PageSeo and SiteSeo shapes, keeping the "wide as CSS, strict where a value reaches the page" rule).
- **Head tags Google actually sees.** The kit ships one pure `computePageHead(layout, siteKit, opts)` function (`kit/seo.ts`) that turns a layout and the site kit's SEO block into the exact `<title>`, meta, link and JSON-LD script tags to put in `<head>`. SSR sites hand its result to their framework's head hook (TanStack Start's `route.head()`, Next's `generateMetadata`; the shape mirrors both), so the tags are already in the initial HTML the crawler downloads. SPA sites use the new `ArmatureHead` React component (rendered near `ArmaturePage`), which sets the same tags via useEffect on the client; the built-in `ArmaturePage` now applies them itself, so an SPA reaches Google without changing any page component. `kit/README.md` documents both paths and how Google sees a non-SSR site (SSR always beats client-only, but the SPA path works).
- **sitemap.xml and robots.txt on every publish.** `builder-publish` now writes `public/sitemap.xml` (every page that isn't noindex, deduped by URL, sorted by path, with the day's lastmod) and `public/robots.txt` (the standard User-agent/Allow lines plus `Sitemap:` when the site URL is set, and any extra rules from Site settings) into the same commit as the changed pages. Both come from `sitemapXml()` and `robotsTxt()` in `kit/seo.ts`. The site URL comes from Site settings › SEO › Site URL; without it, the sitemap still lists paths and robots.txt still allows crawling but skips the Sitemap line. The Search Console setup is verify-with-the-meta-code and submit `https://your-site.com/sitemap.xml` once — no Google Cloud API keys.
- **Tests.** `tests/kit/seo.test.ts` (22 tests) covers the head builder, the JSON-LD for every structured-data kind, the sitemap and robots writers, escaping and the title pattern. `supabase/functions/_shared/builderPublish.test.ts` now proves the publish commit contains a valid `public/sitemap.xml` and `public/robots.txt` with the site URL from the kit, and that a re-publish on the same day does not rewrite either file. `tests/e2e/seo.spec.ts` opens the demo site's production build and reads the tags out of `document.head` (title from the site pattern, description, canonical, Open Graph, Twitter card, JSON-LD LocalBusiness merged from the site's business details, and a builder page's own SEO overrides).

### Changed

- **Fleet is now Projects.** The agency's list of client sites is called Projects everywhere: the route `/projects`, the sidebar item, the page title, "Back to Projects" in a site's menu, the messages the edge functions send, and the docs. The old address `/fleet` redirects to `/projects`.
- **The site switcher is a proper menu.** The site's name at the top of its menu is a button that opens a listbox of every site the person can open (the agency's sites for staff, their own for a client), with a search box from six sites up, arrow keys, Home/End, Enter, Escape (focus returns to the button) and a click outside to close. Choosing a site lands on the same section of that site when it has one (Pages stays Pages; a hosting-only site lands on its Dashboard). It replaces a native `<select>` that always landed on the Dashboard.
- **Pages is the one way into the editor.** The "Edit site visually" button at the bottom of a site's menu and the "Edit your site" button on its dashboard are gone; the dashboard's "Edit a page" card opens Pages, whose rows carry "Edit visually".
- **The Pages table tells the truth and fits a phone.** A page's type comes from what its layout holds: a page that exists only as a layout file, or whose layout root is builder content (anything beyond bare site-section wrappers), is Builder; only a page with no layout, or a layout that merely mirrors its coded sections, is Coded. Builder-native pages no longer read "Coded". "By" is the person's name from their profile (never an id or an email). Row actions are always in view, nothing is clipped, and at phone widths the table becomes stacked cards. Duplicate and Trash stay on pages that exist as a layout alone. The header and footer parts are never listed as pages.
- **Appearance and the editor say what the files hold.** Header and Footer report the true state of each part: coded, or built (how many elements, which menu its Nav Menu shows, or that none is chosen yet), and whether the other part is built and how many menus exist. Menus shows where each menu is shown ("Shown in the header", "Not shown anywhere yet") and, with no menus, whether a built header is waiting for one. The note above a coded header or footer field in the editor now depends on that part: once the header is built it says the coded header no longer shows and points to Appearance › Header, and names the footer as the one still coded.
- **Change requests are asked for from the site's dashboard, not from the editor.** The "Need something bigger?" bar and the inspector's request footer are gone from the visual editor, as is the "Request a change" button on the Stage 1 selection toolbar. In their place: a **Requests** item in every site's menu (clients and agency staff) that opens the existing change-request screens, and a "Need something bigger?" card at the top of the dashboard's Change requests panel with "Request a change". The panel that names an unreadable or locked element keeps its "Request a change here", which carries the element's details.
- **"Unsupported element" is reserved for an element the editor genuinely cannot read** (no id, a duplicate id, no widget type, content settings that are not an object, nested too deep). An element of a known type with one unreadable value now renders with that value ignored: a required content setting (a heading's text, an accordion's items, a text block's document) gets a safe stand-in (`""`, `[]`, an empty document) and is reported like any other ignored setting, and inner elements on a widget that cannot hold any are reported and left in the file rather than turning the element into a placeholder. A publish still puts every such value back exactly as it was.
- **One validator, shipped inside the kit (`kit/validate.ts`, KIT_VERSION 2.3.0).** The zod schemas in `shared/builder/` are gone; the dependency-free validator in the kit is the one set of rules, run by the site when it loads its files, by the site's own content check (documented in `kit/README.md`), by the dashboard when it reads a site and by the publish function before it commits. A site can no longer pass its own checks while Armature rejects its files. `zod` is no longer a dependency of the dashboard or the edge functions.
- **One bad value never takes a page down.** Validation is per element and per property. A setting the validator cannot read is ignored (the element keeps its other settings); an element it cannot read (no id, a duplicate id, no type, content of the wrong shape, children on a widget) is shown as "Unsupported element" in the editor and skipped on the site; the site kit fills anything unreadable from the default kit; the page and the kit always load. Only a file that is not a layout at all (no root, no slug, wrong version) fails to load.
- **Problems in plain English, with a "Show me" link.** The Pages screen lists every value the editor could not read: the page, the element, the setting ("Style › Typography › Font weight"), the value found and what is allowed, each with a "Show me" link that opens the editor on that element. The element's panel repeats the note; an unsupported element's panel explains what could not be read and that nothing is lost. `content-get` returns these as structured `problems`.
- **Publishing never erases or rewrites a value the editor could not read.** Unread values are kept in the file exactly as they were unless the person changes that very setting (`shared/builder/preserve.ts`, applied by the dashboard before it sends and by the publish function before it commits). A *new* unreadable value is refused with the same plain-English message. Unknown keys pass through untouched.
- **Rules as wide as CSS.** Every rule stricter than CSS was loosened; every rule that protects the page (links, media addresses, attribute names, anything emitted into a stylesheet) is unchanged. The full list:
  - Sizes: any decimal or negative number; a bare `0`; unitless values (line-height `1.4`); units `px`, `%`, `em`, `rem`, `vw`, `vh`, `vmin`, `vmax`, `ch`, `ex`, `svh`, `dvh`, `lvh`, `svw`, `dvw`, `lvw`, `pt`, `auto`; a CSS string such as `"12px"`, `"1.4"`, `".5rem"` or a bare number is read into the `{ value, unit }` form. Value range ±1,000,000.
  - Colours: 3-, 4-, 6- and 8-digit hex; `rgb()`, `rgba()`, `hsl()`, `hsla()`, `hwb()`, `lab()`, `lch()`, `oklab()`, `oklch()`, `color()`, `color-mix()`, `light-dark()` with any argument syntax; the 148 CSS named colours; `transparent`, `currentColor`, `inherit`, `initial`, `unset`, `revert`; `var(--name[, fallback])`. Still refused: anything with quotes, semicolons, braces, angle brackets or backslashes, unbalanced parentheses, `url(`, `expression(`.
  - Font families: any family list up to 200 characters, quotes and commas included (`"Helvetica Neue", Arial`), or a kit font reference.
  - Text alignment adds `start` and `end`; border styles add `groove`, `ridge`, `inset`, `outset`, `hidden`; image fit adds `scale-down`; container tags add `main`; flex `justify`/`align` add `start` and `end`; grid templates may use `[named-lines]` and `/`; background size takes any CSS size (`100% auto`), not only `auto`/`cover`/`contain`; gradient angles may be negative.
  - Advanced: `order` ±9999 (was ±99); grow/shrink up to 999; column span up to 48, row span up to 96; position adds `relative` and `sticky`; z-index up to 99,999; animation timings up to 60 s; shadows ±1000 px; CSS classes accept Tailwind-style names (`md:grid-cols-2`, `w-1/2`, `hover:bg-[#fff]`; only `< > " ' & \` are refused) and the renderer no longer strips their punctuation; CSS ids may start with `_`; attribute values up to 2000 characters, 40 attributes; custom CSS up to 50,000 characters.
  - Limits: layout file 2 MB (was 1 MB), nesting 20 deep (was 12), 5000 elements per page (was 2000), rich text 100,000 characters.
  - Numbers written as strings (`"650"`, `"12"`) are read as numbers where a number is expected.
- **The editor never flashes the wrong editor.** Opening the visual editor showed the Stage 1 (content-only) chrome for about three seconds before the builder took over. Until the site answers the handshake, the editor is now a skeleton of the builder layout with "Connecting to your site…"; the Stage 1 chrome, the builder chrome or the existing connection messages appear only once the answer is in.
- **The page is in the URL.** The editor opens the page in its address, `/sites/<id>/visual?page=<slug>`, and every "Edit visually" link passes the page: the Pages screen has an "Edit visually" button per page, the page editor's "Open in the builder", the client sidebar (the page being edited), and the "Show me" links (`&element=<id>`). Home is the default only when no page is given. An unknown page gets a friendly note with a link to the Pages list. The older `/visual/<slug>` form still works.
- **Page menu in the top bar.** Clicking the page name opens a small menu with "Page settings" and "All pages" (back to the site's Pages list).
- **The coded header and footer say so.** Clicking a header or footer field shows a note above its editable fields: clients read "The header and footer are part of the site's code. Your agency can make them editable."; agency staff read "The header and footer are still coded. They become fully editable once converted to builder parts." The words, links and pictures still edit as usual.
- **Audited against the real site (docs/AUDIT.md).** The dashboard and the editor were driven end to end against acts2man/treetestprep running locally (`tests/e2e/real-site.spec.ts`, opt-in with `REAL_SITE_DIR`): every page loads with all of its content, every one of its 140 elements selects with Content/Style/Advanced, drag, image resize, padding, a phone-only override, a Globals change, draft save/reload/restore, publish (GitHub mocked) and the Pages list. Every dashboard screen renders as staff and as a client at 1440 and 390 pixels with no errors and no sideways scroll (`tests/e2e/screens.spec.ts`). The site's own `content/` folder is the fixture for the unit and Deno tests (`tests/fixtures/treetestprep/`; Deno `realSite.test.ts` loads it and round-trips a publish byte for byte).
- **Pages screen fixes from the audit.** Pages created in the visual editor (layouts with no form fields) are now listed with "Built in the visual editor"; the "Header & footer" card no longer offers "Edit visually" (it explains that its words edit on any page) and keeps "Edit fields"; the site's tab bar wraps on phones instead of clipping its last tabs; the Team page's staff list no longer logs a React key warning when a row has no user id.
- **Fixtures from a real site.** `tests/fixtures/treetestprep/` holds the converted site's `content/` folder (layouts, site kit, schema, pages); the unit tests prove every file loads with zero problems and is not rewritten.
- **A coded site section lists what is editable in it.** Selecting a registered (hand-coded) section shows, under its note, an "Editable here" list of the Stage 1 fields the page renders for it (headline, paragraph, picture, button…); picking one selects that field on the page and opens its editor in the panel, exactly as clicking the words or picture on the page does.
- **Drag anywhere.** A dragged widget or element can now land between any two siblings at any depth, before the first or after the last, and inside an empty or nested container. The insertion edge follows the parent's own flow from the layout (a row's direction on the device being edited, reversed rows included, a grid's nearest cell edge) rather than guessing from the rectangles, and the outer few pixels of a container mean "beside it" among its parent's children. While dragging, the container that would receive the drop is outlined and the drag ghost names the target ("after Heading", "before Container", "into Container"). Unit tests cover rows with one child, reversed rows, grids, the outer band and the labels; Playwright covers a drop between middle siblings, left/right in a row, into an empty container, and a move that keeps the element's settings.
- **The canvas handles now look like Elementor's.** Hovering draws a thin outline (solid on a widget, dashed on a container) with the type label. The selected element gets a solid accent outline and a handle tab instead of the floating dark toolbar: a widget's is a square pencil outside its top-right corner (click to edit, drag to move; hovering it reveals parent, duplicate and delete), a container's straddles its top edge, centred, with add / grip / delete (and parent / duplicate on hover); a nested container's tab shifts right so it never sits on its parent's. Inline text editing, the resize handles and the spacing handles are unchanged. A Playwright test covers the outlines, both tabs, the nested offset and selecting at any depth.
- **The panel controls now match Elementor's rows and popovers (KIT_VERSION 2.2.0).** Every control is one row: the label on the left with the device icon right after it, the control on the right; wide controls (a textarea, spacing boxes, a picture) stack under their label. Typography, Text shadow, Text stroke, Box shadow and Border are one row each with a pencil that opens a popover of their fields (live, closing on a click outside or Esc without dropping the selection) and a globe where a global applies (site text styles on Typography, global colours on every colour). A colour is now a swatch button that opens the picker; a linked colour shows a globe on the swatch. Margin and Padding show four labelled boxes with the unit menu and the link toggle on the label line; alignment is an icon group; Width, HTML tag and the new Blend mode are dropdowns. The Text Editor's Content tab is a full rich-text editor in the panel with Visual and Code tabs (paragraph or heading, bold, italic, underline, strike, lists, link, alignment, colour, clear); Code shows the document as sanitized HTML and converts what is typed back, dropping unsupported tags with a notice; the panel and the canvas follow each other live. A container's Layout tab reads Content width (Boxed / Full), Width, Min height, Direction (icons), Justify, Align, Gap, Wrap, a new Structure group that changes the section's columns and moves what is inside into them, then Overflow and HTML tag. New style fields: **text stroke** (`-webkit-text-stroke`) and **blend mode** (`mix-blend-mode`); new Advanced fields for elements inside a grid: **column span** and **row span**. The kit's rich-text serializer keeps a site colour's reference (`data-ae-color`) and a numbered list's start. Tests: structure changes, the HTML round trip, the new CSS; Playwright: the Typography popover with device switching inside it, Esc and outside clicks, the margin link toggle and unit, the Text Editor panel and canvas in sync (Visual, toolbar, Code with dropped tags, and edits from the page), text stroke, blend mode and the Structure group with undo.

A single ~340px panel on the left has two modes — Elements (a Widgets/Globals tab pair, a search box and the widget tiles in a two-column grid) and Edit (the selected element's Content/Style/Advanced, headed "Edit Heading", "Edit Container"… with a grid icon back to Elements; a container's first tab is Layout). Clicking anything on the page opens it in the panel; selecting another element swaps the panel instantly; Esc, the grid icon or clicking empty canvas returns to Elements. A collapse tab on the panel's right edge hides it so the canvas fills the window, remembered per user. Global colours, fonts and typography presets moved to the Globals tab (visible to agency staff and to clients at the style or builder level). The media library is now a modal opened from an image's "Media library" button (reuse, upload and alt text). The top bar follows Elementor's arrangement: a menu (Exit to dashboard, New page, Keyboard shortcuts), "+", History, undo/redo and Page settings on the left; the page name with a chevron to Page settings and the device toggle in the centre; draft status, Preview and a Publish button with a dropdown (Save draft, Save as template, View page) on the right. Page settings and History open in the left panel. A registered (hand-coded) site section selects as a whole and shows a note in its Content tab — clients "Ask your agency to make this section fully editable", staff "convert it to builder elements in the site's repo" — while its text and pictures stay editable on the page. ### Added

- **An agency Clients screen, and Team is staff only.** `Clients` in the agency menu (`/agency/clients`) lists every person who signs in to a site the agency looks after: name, email, the sites they can open, last login and status, with the pending invitations. From there the agency adds a client (a login it creates, or an invite link, on one or several sites at once), resets a password (the new `client-password-reset` function mints a recovery link for the agency to pass on, after checking with the caller's own token that the person is a client of one of its sites; email delivery is a stub, as for invites), resends or cancels an invite, changes which sites a client can open, removes them, and opens **View as client**: the site exactly as that person sees it (client menu, client screens), read-only, with a banner naming whose view it is and an Exit back to Clients. The view is client-side state in the tab (`src/auth/viewAs.ts`): the staff member's own session and rights never change, every write is refused in the browser (`src/lib/readOnly.ts`) before it leaves, and a reload keeps the view rather than quietly restoring full rights on the client's screen. The agency Team screen lists agency staff only. No database change: the screen reads `site_members`, `profiles`, `invites` and `sites` under the existing policies. Covered by `tests/e2e/clients.spec.ts`, `screens.spec.ts` (staff crawl the new route; clients are sent to their site), Deno `clientAccess.test.ts`, and unit tests for the write guard and the view state.
- **Drag an element by itself.** On the canvas an element is picked up by pressing on it and moving a few pixels: under that threshold a click still selects and a double-click still edits, so nothing about clicking changes. Widgets keep their toolbar pencil and containers their tab grip; a container also drags by an empty area of its own (its padding, the gap between its columns). The frame owns the pointer while it is down inside it, so the kit forwards the drag (`armature:element:drag`, kit 2.5.0, `docs/SITE_CONTRACT.md`) and the editor drives the very same indicator and drop as for a toolbar drag; the element is selected when picked up and stays selected after the drop, so the next drag starts at once. The kit swallows the click the browser fires after a drop and refuses its own drag of links and pictures in edit mode.
- **A drag-and-drop proof.** `tests/e2e/drag-sequences.spec.ts` runs 22 drags in a row on the demo site's home page and, with `REAL_SITE_DIR` or `REAL_SITE_URL`, 12 on Tree Test Prep's: up and down between siblings, to the first and last positions, into an empty container, out of a container to its parent's level, left and right in a row, container and section drags by their grips and by an empty area, the same element back-to-back with nothing clicked in between, drags after an undo, and drags whose target is off screen (the editor's own auto-scroll brings it in). After every drop it asserts that the store holds exactly the order the ghost named and the line showed, that the page shows it, that the element is still the selection, and that its next drag starts at once.
- **The demo site runs as a production build under Playwright** (`vite build` then `vite preview`; `DEMO_SITE_DEV=1` for its dev server), and the real site can too (`REAL_SITE_BUILD=1` with `REAL_SITE_DIR`, or `REAL_SITE_URL` for a site already served). The demo's production bundle carried two copies of React (the kit's from the repository root and the demo's own), which the dev server had hidden; the demo's Vite config now dedupes them.
- **The Video widget adds Wistia and a generic embed URL (KIT_VERSION 2.1.0).** Alongside YouTube, Vimeo and a self-hosted file, a video can now be a Wistia media (`wistia.com/medias/…` or `fast.wistia.net/embed/iframe/…`) or any https embed address (a generic player iframe). ### Fixed

- **Drag and drop that stays put.** Investigated on Tree Test Prep's production build; four root causes found and fixed. (1) *Auto-scroll while dragging on a site with `scroll-behavior: smooth`* (this site sets it on `html`): the kit scrolled with `behavior: "auto"`, which defers to that CSS, so every 40 ms tick started a smooth scroll that the next tick interrupted and the page barely moved, or moved after the drop; the kit now scrolls at once. (2) *Auto-scroll speed stuck at the pointer's first depth in the edge band*: the editor's timer captured its step when the pointer entered the band (2 px per tick at the band's edge) and never updated it, so pushing deeper did nothing and a far target took forever; the timer now reads the pointer's current depth. (3) *"Add section" popping up over a section's grip*: the hover "+" between two root sections sits on the same boundary as the selected section's tab and was drawn above it, so a pointer reaching for the grip crossed the gap band, the "+" appeared under it, and the press added a section instead of starting the drag; the "+" is now drawn beneath every tab and handle. (4) *A drop aimed at the first element of a grid cell landing beside the cell*: a container's outer 8 px mean "beside it", and in a grid every edge counted even over a child whose own line would look identical (both horizontal, on the same edge), so "before Heading" turned into "before Container" one level up; over a child the band now yields whenever the two lines would coincide, cell by cell in a grid, and keeps the edges whose line differs (a column's sides in a row or grid draw a vertical line). Also: a held arrow key walked from a stale selection (each press now starts from where the last one landed).

- **Widgets no longer vanish from production builds (KIT_VERSION 2.5.0).** The kit registered its widgets, the widget library's CSS and its glyphs as a side effect of importing `widgets.tsx` and `library/index.ts`. A site whose `package.json` says `"sideEffects": false` (a common line in a Vite site) let the bundler drop those imports from the production build, so every library widget rendered as nothing on the live site while the dev server, which never tree-shakes, showed them all. Registration is now explicit: each module exports its widgets as a table and `createArmatureKit()` registers them together with the library's base CSS and per-widget CSS (`registerBuiltInWidgets`, also exported), so nothing depends on a side-effect import; a widget a site registered itself is left alone. `tests/e2e/production-build.spec.ts` builds `examples/demo-site` for production laid out as a real site (the kit under `src/lib/armature-kit/`, `"sideEffects": false`), serves the built files and checks in a browser that one element of every widget type renders with its CSS and glyphs and that tabs, panels and the countdown run (`/every-widget`, from `src/every-widget.json`; `tests/kit/widgets.test.ts` keeps that page, the validator and the kit's widget list in step). The demo site keeps `"sideEffects": false` so the whole Playwright suite runs the realistic configuration. `kit/README.md` (step 8) and `docs/SITE_CONTRACT.md` now require verifying a site against a production build (`npm run build && npm run preview`), since a dev server hides this class of bug.
- A client who opens an agency-only address (Users, Site settings, and now `/github/setup` too) sees a proper heading, a short explanation and a "Back to your dashboard" link instead of a bare warning; the not-found screen has a heading of its own. Both were noted in `docs/AUDIT.md`, whose notes now record them as fixed.
- **A font weight of 650 no longer blanks a page.** The first real converted site (treetestprep) uses variable font weights (`font-weight: 650` on its hero headline and in its site kit). The old rules allowed only 100…900, so one number invalidated the whole home layout and the whole site kit: the Pages screen showed "Invalid input", the visual editor showed an empty Home page with only the footer, and the default kit silently replaced the site's colours and fonts. Font weight now takes any whole number from 1 to 1000 plus `normal`, `bold`, `lighter` and `bolder`; the Weight control keeps its list and adds a "Custom…" entry that takes any number.
- **The canvas sheet can no longer be scrolled out from under the overlays.** A `scrollIntoView` inside the site's frame (the kit's own, or a browser's) could also scroll the editor's overflow-hidden sheet by a few dozen pixels, so the frame and every overlay drawn above it shifted while drags and handles still measured from the sheet's top; the sheet now snaps back to zero on any scroll, and drag hit testing accounts for a scroll offset anyway.
- **An element's own settings now always beat a CSS class attached through Advanced > CSS classes (KIT_VERSION 2.1.0).** Sites converted from hand-coded sections keep their legacy classes on the element (Advanced > CSS classes); when the site's own stylesheet loaded after the kit's, a `.ae-root .legacy` rule could out-order and override a Style-tab value the person set in the builder. The CSS generator now emits every per-element rule through a doubled element class (`.ae-root .ae-<id>.ae-<id>`, specificity 0-3-0), so an element's Style, layout, spacing and Advanced values outrank any legacy class regardless of load order. A new unit test proves the element rule's specificity beats both `.promo` and `.ae-root .promo`.

- **The kit no longer changes how a registered site section renders (KIT_VERSION 2.0.1).** The kit's box-sizing reset (`.ae-root *`, `::before`, `::after`) leaked into hand-coded sections rendered inside `.ae-root`, forcing `border-box` on their elements and pseudo-elements — on Tree Test Prep it shrank a bordered `::before` arrow circle from 30px to 26px. Every kit reset and base rule now excludes `.ae-site-section` and everything inside it with a zero-specificity `:not(:where(.ae-site-section, .ae-site-section *))`, so a site section keeps the browser defaults it was written against. A new Playwright test in `examples/demo-site` (`/section-parity`) renders one section bare and through `<ArmatureSlot>` and asserts they are pixel-for-pixel identical, so builder CSS can never change a section's rendering again.
- "Add a site" / "Check connection": the step "The App can write to the repository" now passes when the installation token GitHub issued carries Contents: write. It used to read `permissions.push` from the repository response, which GitHub does not report reliably for App installation tokens, so the step failed on real deploys right after the token step had passed.

## [0.1.0] - 2026-09-21

The first version: a manual-only editing dashboard. No AI features anywhere.

### Added

**Dashboard**

- Sign in with email and password or with an emailed sign-in link; create an account; reset a password.
- Invite acceptance page: a person opens the link, signs in or creates an account with the invited email, and is added to the site or agency.
- Fleet: every site with status, last publish and open change-request count; "Add a site" flow that installs the GitHub App, links the installation, and runs the connection checklist.
- Client home: the site, recent publishes, change requests, and the way in to editing.
- Pages list built from the site's `content/schema.json`.
- Page editor ported from the pilot: local draft, per-field Changed tags, Revert, Discard all, one Publish button, blocked-reason line, leave-page warning, three-state connection line that can never be blank, Check connection checklist, conflict panel, and images resized in the browser to WebP (2000 px longest edge, 3 MB cap).
- Change requests with screenshots in Supabase Storage; the agency sets a status and a note; the client sees updates.
- Team: invite clients to a site, see who has access, remove access, see pending invites.
- Agency settings: portal name, logo URL and accent colour, applied to every client's portal. Clients never see the word Armature.
- Publish history per site with a link to each commit and the reason for any failure.

**Publishing**

- Seven Supabase edge functions: `github-setup`, `site-connect`, `content-get`, `content-publish`, `site-diagnose`, `invite-create`, `invite-accept`.
- GitHub access through a GitHub App only: an RS256 app JWT signed with Web Crypto mints a one-hour installation token per request, scoped to the one repository.
- The pilot's publish engine, ported: schema validation, URL and image rules, one commit per publish through the Git Data API, no force-push, field-level conflict merge, re-validation of the merged file before commit, errors that are never silent, secrets that stay server-side.
- A `publishes` row for every attempt on a site the caller can access (committed, conflict or failed).

**Data and security**

- Postgres schema for agencies, members, GitHub installations, sites, site members, invites, publishes, change requests and attachments, with a `profiles` mirror of `auth.users`.
- Row-level security on every table, SECURITY DEFINER membership helpers, and a plain-SQL test proving that a client of site A cannot read site B and a member of agency X cannot read agency Y.
- A private storage bucket for screenshots, scoped by site id in the object path.
- `bootstrap_agency()` to turn the first sign-up into the first agency owner from the SQL editor.

**Site contract**

- `docs/SITE_CONTRACT.md` (v1): `content/schema.json` with `armatureContract: 1`, `content/pages.json`, `public/assets/uploads/`, and a minimal example that the tests keep valid.
- A package-free `shared/` folder used by both the browser and the edge functions.

**Docs and tooling**

- `docs/SETUP.md`: every click, for a non-developer.
- `npm run verify` (typecheck, lint, tests, build, secret grep), Deno checks and tests for the functions, `npm run db:test` for the migrations and RLS proof.
- GitHub Actions: CI, and a terminal-free edge-function deploy.
- Netlify configuration with the single-page-app redirect.

### Known limitations and stubs

- Email sending is a stub. `invite-create` logs the invite link and returns it to the agency, who copies it to the client. The dashboard says so.
- No preview of unpublished changes (the visual editor now shows drafts live; the form editor still does not).
- Publishing is per page in the form editor (the visual editor publishes every page in one commit).
- Agency logos are given as an https URL, not uploaded.
- Migrations are applied by hand in the Supabase SQL editor; there is no automatic migration runner.
- Sign-up confirmation and password-reset emails use Supabase's default templates and sender.
